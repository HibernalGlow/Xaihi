## 二、为什么

原先的审计判断分层是对的：remote artifact 能从真路由取回，不代表客户端已经把它变成 React 组件，也不代表组件已经在正式文档里上屏。现在补的是“装载 → 入口归一化 → 宿主能力投影 → React 渲染 → 用户事件”这一条挂载腿。

这次没有把 Kisaki 真界面改造成 remote。ADR-0014 已经确定第一方节点通过生成的 in-realm 注册表渲染，MF2 负责第三方插件贡献；因此验收夹具是仓外形状的独立 remote。这样同时避开了 `@/` 构建期别名无法随 MF2 运行时共享、以及 profile 不得依赖仓内 `@hibernalglow/*` 的边界。

清单仍由 DSH 生成和提供。浏览器只消费 `/xaihi/manifest.json` 和 artifact route，不启用搬来的 TOML、本地安装记录或另一套安装 authority。remote 的 `requires` 不会被清单自动投影成能力；当前文档没有可用的 DSH 命令调用身份，所以命令面明确返回 proposal P1。

MF2 runtime 的卸载能力也按实测能力实现：撤掉 Xaihi 自己的登记、贡献和后续装载入口，已经评估过的 JS module/script 不能被浏览器撤销。清单刷新采用窗口 focus 触发；没有另开 SSE，因为 DSH 的配置事件白名单与本验收目标无关。

## 三、与 DSH API 的关系与实测读数

- Core 侧的 workspace 文档由 `buildWorkspaceDocument` 生成，manifest 中的 remote 地址形状来自 `packages/core/src/registry.ts:148-156`：`/xaihi/remotes/<slug>/<rev>/<entryFile>`。测试服务直接使用 `manifestHandler`、`remoteHandler` 和 `uiBundleHandler`（`packages/ui-host/tests/mf2-server.ts:5-7,50-55`），因此 HTTP 路由和响应体来自生产 Core handler；它没有启动 DSH 宿主进程，不能写成“真实 DSH 新客户端宿主已部署”。
- 文档入口在 `packages/ui-host/src/document/main.tsx:57-72`，通过 `DocumentBridgeProvider` 接入 DSH 文档桥，并挂载 `DshRemotePlugins`。MF2 remote 通过 `frontendRuntime` 的 `createInstance` 和 `registerRemotes` 注册；共享范围绑定宿主 realm 已加载的 React 模块（`packages/ui-host/src/plugins/frontendRuntime.ts:107-160`）。

## 四、后续扩展

1. 在一台隔离的开发 DSH host 上部署本批 `ui-host` 产物，再用 `pnpm host` / `host:headless` 的标准面重复 iframe 挂载判据；目前共享 3199 只作为传输活体证据，未替换其运行中的客户端。
2. 若要让插件声明命令、文件或其他宿主能力，先补 DSH 文档桥的真实调用身份和对应服务映射，再把 `requires` 从当前可见拒绝改成有证据的授权投影；不得在远端 manifest 上伪造 grant。
3. 对生产远端构建补发布侧检查：remote 产物要提供可验证的 integrity/origin 记录，且插件包的 `files` 必须把实际产物纳入发布包；本轮夹具使用的是 Core 内存注册与临时 rspack 目录。
4. 保持第一方 Kisaki 走 in-realm 生成注册表；若未来要支持其他第三方 UI 贡献，继续沿 `xaihi.manifest/1` 的稳定 contribution id 扩展，不把 `Panel.tsx` 占位页当作 MF2 验收替身。
